Technical due diligence

Béa — engineering assessment

A read of the codebase behind Béa, a travel memory and planning app, for the purpose of an investment decision. Findings are ordered by what should change the decision, not by what is easiest to fix.

Repo: larochellemathildeeva-oss/beabuddy Commit: b7d30f2 Version: 8.4.3 Date: 17 Sep 2026

Verdict

The engineering is better than the stage of the company. Authorization is correct everywhere I could check it, the security thinking is unusually mature for a twelve-day-old codebase, and the test suite covers the logic most likely to produce silent data errors. I found no architectural dead ends.

The risks are operational and human, not structural. One person and an AI assistant wrote all of it in twelve days; the production database is updated by hand; there is no monitoring, no spend cap on the AI features, and a core feature depends on a free public server whose operators ask people not to use it in production. Every one of those is fixable in weeks.

Recommendation: proceed, with conditions. Make funding contingent on the 30-day remediation list below, and treat key-person risk as the dominant term in the valuation rather than code quality.

Findings · critical

Issues that should shape the terms

These four carry real probability of becoming expensive. None is a reason to walk away; each is a reason to attach a condition.

F1

The entire company is one person

Key-person
Evidence
108 commits between 5 and 17 September 2026, from two identities: the founder (53) and an AI assistant (55). No second engineer has ever committed. Infrastructure — Supabase, the Canner deploy, the domain — appears to sit in personal accounts.
Risk
If the founder becomes unavailable, there is no one who has read this code. Roughly half the commits were AI-assisted, which means institutional knowledge lives in a chat history rather than in a second head.
Fix
Move every credential into a company-owned vault with a break-glass procedure before money moves. Fund a second engineer in the first hire. Require an architecture decision record for each subsystem — the repo already has AGENTS.md and docs/BRANDING.md, so the habit exists and only needs extending to technical decisions.
Effort
Credentials: days. Second engineer: a hiring cycle.
F2

Production schema changes are applied by hand

Data integrity
Evidence
28 migration files; five state it outright — "Applied by hand — writing this file does not change the live database alone." The deploy runs no migration step. Two features shipped to production this month and sat inert until someone remembered to paste SQL into a dashboard: trip_todos and reco_shares.
Risk
Nobody can prove the production schema matches main. There is no scripted rollback. A migration applied wrongly at 2am on a Sunday is the single most likely cause of irreversible customer data loss in this system.
Fix
Adopt the Supabase CLI migration flow in CI: apply to a staging project on every merge, promote to production on release. Add a drift check that fails the build when a repo migration is unapplied — the app already detects this at runtime per feature (isMissingTodosTable), so the signal exists and just needs lifting into CI.
Effort
1–2 weeks including a staging project.
F3

No per-user cap on AI or geocoding spend

Cost exposure
Evidence
Every AI-backed server function requires a signed-in user — good — but none counts calls. There is no usage ledger table anywhere in the schema. The only limits are Google Gemini's own, applied to the whole account. The team knows: the internal security backlog lists "App-level AI / geocode quotas" as P1, status Partial.
Risk
One motivated user, one scripted loop, or one stolen session can exhaust the company's entire AI budget and take the feature down for everyone. Cost scales with abuse, not with revenue.
Fix
Add a ai_usage ledger keyed by user and day, checked in the existing requireSupabaseAuth middleware so every function inherits it at once. Daily per-user cap, alert at 80% of the account budget. The invite system already demonstrates this exact pattern with trip_invite_attempts — it is a copy of working code.
Effort
3–5 days.
F4

Directions run on someone else's free demo server

Third-party
Evidence
Routing calls router.project-osrm.org, the OSRM project's public demo instance, which its operators state is not for production use. Geocoding calls Nominatim, whose usage policy the code respects by sleeping 1.1 seconds between lookups — so building directions for a twelve-stop day takes over thirteen seconds of wall clock before anything renders.
Risk
The feature can be throttled or cut off without notice, by a third party with no obligation to the company. The mandated sleep is also a permanent, unfixable performance ceiling on a headline feature.
Fix
Move routing and geocoding to a commercial provider — Mapbox, Geoapify or HERE. This removes the terms exposure, the outage risk and the sleep in one change. Avoid Google Maps Platform specifically: its terms forbid storing place data beyond a short cache, and storing saved places permanently is the entire product.
Effort
1 week; the call sites are two functions.

Findings · material

Issues to fix before scaling the team

F5

No component or end-to-end tests

Quality
Evidence
491 tests, all of them over pure functions in src/lib. 21 hooks and 33 components have none. Nothing exercises a real user journey, an auth redirect, or an RLS policy.
Risk
The untested layer is where users actually live. A concrete example from this month: a public marketing page shipped with a redirect that bounced signed-out visitors to the sign-in form — on the one page written specifically for people without accounts. Type checks and unit tests both passed. It was caught only because someone rendered it by hand.
Fix
Playwright against a seeded test Supabase project, covering five paths: sign up, save a place, build a trip, share a list, delete an account. Add an authorization test that signs in as user A and asserts it cannot read user B's rows — that is the test which protects the company's reputation.
Effort
2 weeks, then hours per feature.
F6

The lint gate cannot fail

Process
Evidence
CI runs lint with continue-on-error: true, and main currently carries 1,106 lint errors. Typecheck, test and build do block, correctly.
Risk
Low technically — nearly all are formatting. Culturally it matters: a permanently red check teaches everyone to ignore checks, and hides the day a real rule fires.
Fix
Run the formatter across the tree in a single commit, then delete continue-on-error. This is an afternoon and it should be done before a second engineer ever sees the repo.
Effort
Half a day.
F7

Production is unobservable

Operations
Evidence
No error reporting, no performance monitoring, no product analytics anywhere in the dependency list or the source. The internal backlog flags a related gap: "Analytics inventory vs Privacy", P1, Open.
Risk
Every production failure is invisible until a user reports it, and most never do. There is also no evidence base for product decisions — retention, activation and drop-off are all unmeasurable today.
Fix
Sentry for errors and a privacy-respecting analytics tool (PostHog EU or Plausible) for behaviour. Update the Privacy Policy in the same change — the app already has a consent system, so the disclosure path exists.
Effort
2–3 days.
F8

A few files carry too much

Maintainability
Evidence
routes/trips.tsx is 1,541 lines; ItineraryImport.tsx 1,295; routes/recommendations.tsx 1,055. Together they hold most of the product's complexity.
Risk
These are the files a new engineer must read first and the ones least safe to change. Review quality drops sharply past a few hundred lines.
Fix
Extract by section, not by arbitrary size. The repo already contains the right pattern — TripSection and TripBanner were pulled out of trips.tsx recently — so this is continuing established work, not a rewrite. Target under 400 lines per route.
Effort
1 week, incremental, safe to do between features.

Findings · minor

Worth a ticket, not a conversation

F9–F12

Four small items

Low
  • Sample data ships to every user. The 722-line demo seed is imported by the home, help and opportunities routes, so it downloads whether or not anyone loads samples. Move it behind a dynamic import() at the button.
  • Hydration mismatch on public routes. React reports a server/client attribute mismatch on at least two pages. Harmless today; it disables server-rendered markup reuse and can become a visual bug. Trace it in the shared shell.
  • Accessibility is unverified. 267 buttons against 92 aria-labels, and many controls are icon-only. Add eslint-plugin-jsx-a11y and an axe pass in the E2E run; this is also a procurement blocker for any B2B channel later.
  • One P0 remains open internally. The security backlog lists "Supabase Auth dashboard unknowns" as P0, Open — meaning auth provider settings have not been audited against the documented posture. Close it; it is a settings review, not a build.

The other side

What is genuinely good here

An audit that only lists faults misprices the asset. These are the things most seed-stage codebases get wrong, and this one did not.

✓ Authorization is correct

Row-level security is enabled on all 22 tables, and all 25 server functions carry the auth middleware. Cross-user data leakage is the most common fatal flaw in apps at this stage. It is not present.

✓ Security has been thought about, in writing

A triaged backlog with P0/P1 severities, invite-code guessability worked out mathematically, expiring single-use invites with throttled attempts. This is unusual discipline for twelve days of work.

✓ The document vault is real encryption

AES-GCM with a PBKDF2-derived key, performed in the browser before upload. The claim made to users — that the operator cannot read contents — is supported by the implementation.

✓ Privacy defaults favour the user

Sharing sends a snapshot rather than access, personal notes are excluded unless explicitly opted in, and account deletion is implemented with double confirmation.

✓ The tested layer is the right one

491 fast tests concentrated on parsing, deduplication, geography and date handling — the logic where silent wrongness corrupts user data rather than throwing an error.

✓ Clean dependencies

Zero known vulnerabilities, no secrets committed, and a modern stack that a competent hire can be productive in without a bespoke onboarding.

Remediation

What I would require, and by when

Days 0–30

Conditions of funding

  • Credentials moved to company ownership with documented recovery (F1).
  • Per-user AI and geocoding quota shipped (F3).
  • Formatter run, lint gate made blocking (F6).
  • Error monitoring live (F7).
Days 30–60

Operational maturity

  • Staging project plus CI-applied migrations and a drift check (F2).
  • Routing and geocoding moved to a commercial provider (F4).
  • End-to-end suite over five paths, including a cross-user authorization test (F5).
Days 60–90

Ready for a second engineer

  • Large routes decomposed; architecture decisions written down (F1, F8).
  • Accessibility linting and axe checks in CI (F9–F12).
  • Remaining P0 and P1 items in the security backlog closed or formally accepted.

Scope and limits of this audit

This is a static review of source code at commit b7d30f2. I had no access to the production database, no signed-in session, and no ability to run the application against real data. Authorization findings are therefore read from migration files and middleware, not proven against a live instance.

Three things are consequently unverified and should be checked before closing: that the production schema matches the repository; that row-level security behaves as written under a real second user; and that the deployed build corresponds to this commit. Each is an hour's work for someone with credentials, and F2 exists precisely because the first cannot currently be answered from the repository alone.
